# U9D12 无线回包调查与局部候选修复（2026-11-02）

本分支是实验候选，不是新固件发布。现机仍使用 U9D12，临时模块已恢复。2.4 GHz 剩余尖峰和 64/160 MHz 双 SSID 漏扫均未宣称解决。

## 已定位的等待

通过内核 ICMP 收发时间戳和每 10 ms 一次的只读、按站点软件队列快照，同轮 80 个探测包 RTT 平均 42.63 ms、P95 108 ms、最高 180 ms；内核收包到提交回复平均 0.22 ms，最高 2.45 ms。多个长 RTT 同时出现 90–170 ms 的驱动软件队列驻留，手机已处于 PWR_ACTIVE，而驱动仍在 CR_PADDING 或 START_PS。

这是站点队列相关证据，不是逐 skb 成员追踪。手机与路由器时钟偏移未知，绝对单向值不能直接相减作为真实单向时延。此前高输出量的 TxS 诊断扰动了时延，不作性能验收依据。

## 本分支代码

MT7603 PCI 驱动在等待全局 PS 检索请求寄存器的 CR_PADDING 状态时，该站点自身尚未开始硬件检索。原逻辑在站点已经唤醒后仍阻止其软件队列出队，直到别的站点事件推进请求。

候选允许已唤醒且处于 CR_PADDING 的站点出队，并在 SAVE→ACTIVE 时请求排空；保留 CR_PADDING 和原 pending FIFO 项，防止再次入睡造成重复排队。START_PS、GOING、WAIT_EVENT 和实际睡眠站点仍受原保护。仅限 MT7603 PCI 条件。

原函数和实际出队条件被提取进行回归：12 组状态/模式组合、普通唤醒、睡眠保护、pending FIFO 保留及再次睡眠不重复排队。原版及候选均通过 native ASan/UBSan 与 MIPS/qemu。测试是有限状态回归，不证明真实硬件并发或长期稳定性。

实机 RAM 试验：候选空闲 80 包 RTT 平均 31.16 ms、P95 101 ms、最高 113 ms；软件队列最长约 100 ms，剩余长等待处于 START_PS。负载下下/上行约 100.79/88.05 Mbps，两组 48 次 ping 无丢包，但最高 209/222 ms，整体延迟目标仍未达到。单轮前后值不构成长期性能保证。

## 未采纳的试验

在局部候选上恢复原驱动中被注释的 MCU 通知调用，首轮 80 发 73 收，缺失的都是最初 7 包；该轮未等待桥接转发就绪，不能归因于芯片通知。补测明确等待桥接进入转发并静置后，80/80 收到，RTT 平均 35.21 ms、P95 107 ms、最高 150 ms，START_PS 等待仍存在。因此未采纳 MCU 通知补丁，且需要审查请求状态发布与固件事件并发顺序。

64/160 MHz 临时将 VHT Operation 从新版 width=1/中心段 58,50 改为旧版 width=2/中心段 50,0；电脑确认两个新鲜广播及准确 IE 后，手机在连接主网时连续三次扫描仍缺失访客。此假设失败，已恢复原编码、100 TU、关闭访客。既有 36–60 信道通过记录不重复测试。另一轮原版负载测试与 5 GHz 重载存在时间重叠，不作为干净的性能对照。

## 后续与复现

下一步应在有充足恢复时间的维护窗口继续跟踪 START_PS 请求、固件事件和 wake 的先后关系，避免简单取消检索保护或无限增加队列。64 主信道问题仍需终端固件扫描与 AP 广播联合证据；本实验不能归咎某一方。

测试脚本需要两个源码树：基线为本实验提交的父提交，候选为本分支。依赖 cc、ASan/UBSan、qemu-mipsel 和 MIPS musl gcc：

```sh
python3 tests/mt7603-ps-wakeup/test_ps_wakeup.py --baseline-tree /path/to/baseline --candidate-tree /path/to/candidate --mips-cc /path/to/mipsel-linux-musl-gcc --work-dir /tmp/mt7603-ps-tests
```

公开内容仅含源码、有限状态回归和脱敏结论，不含用户配置、无线凭据或原始设备日志。稳定 main 与已验收 U9D12 分支保持原样。
